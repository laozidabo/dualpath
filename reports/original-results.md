DualPath 小规模对照实验与独立复核报告

实验记录：2026-10-30；独立复核：2026-10-31。

**结论：这次实验观察到 DualPath 能修复直接作答的错误，但没有观察到它优于自审。** 在 30 道自建 Python 函数题上，直接作答通过 26 题，五轮自审和 DualPath 都通过 28 题，而且两者每一道题的通过/失败完全一致。DualPath 的平均估算成本比五轮自审高约 22%。这是一个可复验的小规模初步结果，不能据此宣称一般性的优越性，也不能证明两种方法等效。

我对这个想法的判断是：主动探索错误路线有工程价值，但目前证据尚未显示，独立错误线路、逐项概率评估和多阶段汇聚，相比简单自审提供了独有收益。下一步应验证这些组件各自的贡献，并改善结构化输出可靠性。

**主实验结果**

| 方法 | 完整通过题数 | 通过率 | 每题平均输入＋输出 tokens | 每题平均估算费用 |
|---|---:|---:|---:|---:|
| 直接作答 | 26/30 | 86.7% | 684 | ¥0.00162 |
| 五轮自审 | 28/30 | 93.3% | 18,836 | ¥0.03361 |
| DualPath | 28/30 | 93.3% | 23,379 | ¥0.04103 |

费用和 tokens 包含每组使用的共同初稿；DualPath 还包含一次失败请求的预留及其整组重跑开销。因此每组费用相加会重复计算初稿，不能作为实际总支出。相对自审，DualPath 平均多用约 24.1% tokens，估算费用高 22.1%；剔除发生重跑的 DP003 后，费用仍高约 16.6%。缓存命中取决于本次运行条件，这些数字不是未来独立部署的价格保证。

两种改进方法相对初稿均为 2 胜、0 负、28 平；精确配对 McNemar 检验 p=0.5。DualPath 对自审是 0 胜、0 负、30 平。数据没有提供显著优势证据。仅作描述参考的 Wilson 95% 区间为：直接作答 70.3%–94.7%，另两组 78.7%–98.2%。这些区间的总体推断依赖任务独立、具有代表性等假设，本次自建任务并不充分满足这些条件。

**实验具体做了什么**

- 固定项目版本为 [ff23e7e](https://github.com/laozidabo/dualpath/tree/ff23e7e07db44b2c11fb9d60ec946439958757f6)，使用其原有提示词、问题排序和汇聚流程；错误线路最多发现 5 个问题，检索关闭。
- 30 道事先冻结的自建 Python 函数题，包含明确规则、公开例子、隐藏断言、参考实现和每题一个故意植入错误的实现。每题每组仅采样一次；不是公开标准基准，也不是随机抽取的真实业务任务。
- 请求模型名为 `deepseek-flash`，temperature=0.2，关闭 thinking，每次最多输出 2048 tokens。626 个成功响应均返回同一模型名和同一 system fingerprint。官方当日文档将这个模型名对应到 DeepSeek-V4.1-Flash-1017；响应没有给出可独立固定的权重版本。[DeepSeek 模型与价格文档](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)
- 三组共享同一份直接作答初稿。自审执行 5 次“反馈→重写”；DualPath 独立探索错误，再与初稿汇聚。两者计划上限都是初稿加 10 次调用，但实际 token 数不相等。
- 模型只能看到题目及本方法的中间输出，没有获得隐藏测试执行反馈或参考答案。审计通过逐条回放验证请求内容来自这条冻结流程。
- 评分是整题隐藏测试全部通过才计 1 分。代码在隔离的 Linux bubblewrap 环境执行，禁止网络、限制内存和时间；方法解析失败也计失败。隔离保护宿主环境，但测试不是对蓄意篡改 Python 进程内测试机制的安全证明。

共享初稿适合比较修正能力，但改变了原始并行调度。原日志中的延迟还受共同 API 队列、任务并发和重试影响，因此本报告不据此声称 DualPath 更快。

**四道失败/修复题说明了什么**

| 题目 | 直接作答 | 五轮自审 | DualPath | 核查结论 |
|---|---|---|---|---|
| DP005：稳定拓扑排序 | 失败 | 失败 | 失败 | 空任务时提前返回，未拒绝引用未知任务的依赖；题面规则优先级存在歧义 |
| DP012：版本号比较 | 失败 | 通过 | 通过 | 初稿的正则匹配接受末尾换行；两种方法都改为严格全字符串校验 |
| DP026：资源排程 | 失败 | 失败 | 失败 | 初稿和自审把空区间当成冲突；DualPath 因错误清单截断而未产出答案 |
| DP029：记账事件聚合 | 失败 | 通过 | 通过 | 初稿未按规定拒绝已经取消但载荷冲突的同 ID 记账；两种方法均修复 |

最小复现输入已单独在沙箱验证并保存在 `audit/minimal_cases.json`：

- DP005：`schedule_tasks([], [('a', 'b')])`。冻结测试要求 ValueError，但“空任务返回 []”与“依赖引用未知任务抛异常”的优先级没有明确写出。保留原始计分，同时报告排除此题的结果；不把它当作明确的算法能力缺陷。
- DP012：`compare_versions('1.2.3\n', '1.2.3')` 应抛 ValueError。题目明确禁止空白，没有 DP005 的规则冲突。
- DP026：`schedule_jobs([('a', 0, 4, ['r'])], {'r': [(2, 2)]})` 应返回 `[('a', 0, 4)]`。DualPath 在调用 300 的发现阶段达到 2048-token 上限；截断 JSON 经原解析器提取后不再是数组，触发 `ValueError: 错误线路的发现阶段必须返回 JSON 数组`。这次失败体现输出协议的脆弱性，无法判断未完成流程本来能否修好排程代码。
- DP029：`project_balances([('cancel', 'x'), ('post', 'x', 'a', 5), ('post', 'x', 'a', 6)])` 应抛 ValueError，即使记账已取消也不能忽略冲突。

**他人接续工作的审查与协议偏离**

接续者增加了 `resume.py`，在一个接口请求失败后恢复了实验。原始数据集、提示词、实验主程序、评分器和 vendored 项目代码的 SHA-256 均与冻结协议一致，未发现这些内容被事后改写。

调用 305 是 DP003 的概率评估请求，日志只保留 `RuntimeError`，没有足够信息判断具体 HTTP 状态或网络原因。恢复程序保留初稿和已完成的自审，只重跑 DP003 的 DualPath 条件。首次尝试有 6 次追加请求，恢复又有 10 次，加上共享初稿，这个条件累计计入 17 次请求，超过原计划的 11 次。因此不能将整个实验描述成严格等调用预算、从不重试的评测。

成功恢复后原 incomplete 文件已删除；审核依据是保留下来的完整请求序列、恢复代码、结果恢复标记以及离线回放，不能追溯所有已删除的中间文件。费用核算保留了失败和重跑开销，没有只记成功尝试。

事后敏感性检查如下，均不替代冻结主结果：

| 纳入题目 | 直接作答 | 五轮自审 | DualPath |
|---|---:|---:|---:|
| 全部 30 题 | 26/30 | 28/30 | 28/30 |
| 排除重跑题 DP003 | 25/29 | 27/29 | 27/29 |
| 排除歧义题 DP005 | 26/29 | 28/29 | 28/29 |
| 同时排除两题 | 25/28 | 27/28 | 27/28 |

“未观察到 DualPath 优于自审”的结论在这些口径下保持不变。若衡量首次尝试的端到端可靠性，并将 DP003 的基础设施失败也算失败，DualPath 为 27/30；这是另一种口径，不是恢复后的代码质量主分数。

**实际花费与本轮复验**

保存的计费请求共 627 次，626 次有成功响应、1 次失败；已返回用量为输入 896,798 tokens、输出 349,117 tokens。请求起始时间覆盖北京时间 2026-10-30 18:50–19:18，均在空闲时段。按官方空闲价格（每百万 tokens：缓存命中输入 ¥0.02、未命中输入 ¥1、输出 ¥4）独立重新核算，成功请求估算为 **¥2.15919024**；加失败请求的保守预留 **¥0.03132**，合计 **约 ¥2.19**。未核对账户实际账单，因此这不是扣款证明。用于预算保护的高峰价格保守账本合计 ¥4.34970048，仍低于授权的 ¥10。[计价来源](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)

本轮审查新增模型付费调用为 0。完成的离线验证包括：

- 全部 90 份最终答案重新评分，与原记录完全一致。
- 30 份参考实现全部通过，30 个预置错误实现全部被拒绝；这验证了这些控制样例，不能证明测试穷尽所有错误。
- 对完整请求链精确回放，核对各阶段输入、最终输出和 DualPath 中间结构；同时重现基础设施失败尝试及 JSON 方法失败。
- 从原始 usage 独立重算费用及分组指标；核对调用编号、模型参数、共享初稿、文件哈希。
- 原有 22 项单元测试全部通过，包括隔离环境、预算预留与恢复逻辑。

**补充发现：一轮自审可能是更实用的比较基线**

在已有轨迹中取第一次“反馈→重写”的答案，新增进行离线评分，得到 **27/30**，每题平均 **4,502 tokens、¥0.00922**。相比五轮自审，费用约低 72.6%，少通过 DP012 这一题。这里只提取已有的第一轮，未向模型提供测评反馈，也未重新采样。

这是看过主结果后增加的分析，不能当作预先规划的第四个实验组，更不能据此断言一轮最佳。它提供了后续可检验的方向：在新题集上比较一轮自审、五轮自审和按明确规则停止的审查，衡量每增加一次调用换来多少修复。

**建议接下来怎么推进**

1. 先解决结构化输出失败：给发现阶段设置简短字段约束，显式识别截断与数组结构错误；保留清楚的失败状态，设计计入预算的恢复策略。对 DP026 的录制响应做回归测试，不把修复后的程序覆盖本次冻结证据。
2. 新实验同时加入一轮自审基线，并按实际 tokens/费用控制预算。当前同调用上限并不能消除计算量差异。
3. 做组件消融：保持模型和总预算一致，分别去掉概率评分、独立错误线路或某次汇聚。只有这样才能判断复杂度是否有用。当前“概率”来自模型自行判断，尚未验证校准，不应作为真实发生概率宣传。
4. 在新的、提前冻结的题集上测试；明确 DP005 这类规则优先级，增加更难任务并考虑跨模型、多次采样。不要围绕已经公开的这 30 题反复调参后继续使用同一成绩作为泛化证据。

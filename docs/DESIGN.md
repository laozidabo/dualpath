# 设计说明：v0.2 为什么改成失败先行、证据驱动

本文记录 v0.2 的核心取舍，供后续维护和审阅使用。结论都以已归档的三轮小样本实验和现有实现为边界，不构成对模型能力的一般性判断。

## 1. 为什么去掉概率分级

v0.1 的 `run` 模式要求模型为每个探索出的问题给出出现概率，再按概率划分等级。这个做法有三个难以回避的问题：

1. **概率没有校准。** 这些数字来自模型对当前任务的判断，没有历史频率、没有可重复的测量过程，也没有任何事后校准。一个写着「80%」的问题，并不对应 80% 的实测发生率；把它展示为概率会暗示不存在的统计依据。
2. **相对排名不等于风险等级。** 即使模型能大致排出「问题甲比问题乙更可能发生」，也不能推出甲比乙更值得优先处理。风险还取决于后果严重程度、可检测性、修复成本和触发条件，单个概率数字容纳不了这些维度。
3. **分级会制造确定性错觉。** 「一级问题」「二级问题」这样的标签容易被读成经过评估的风险结论，而实际只是同一轮模型输出的次序。旧实验也显示，错误清单截断、结构化输出失败等问题会让这套分级在关键时候不可靠。

作为对照，FMEA 也使用发生度、严重度、探测度这类主观评分，但它至少要求事先定义评分尺度、记录评分依据，并由团队复核。DualPath 的概率分级没有这些约束，继续保留只会把未经验证的估计包装成风险等级。因此 v0.2 在 `review` 中不再输出概率或百分比。

## 2. 为什么保留「失败先行」

「失败先行」指先枚举任务可能怎样失败，再决定是否需要修改方案。它仍然有价值的理由：

- 明确要求列出失败机理和触发条件，能把「可能有问题」变成可检查的陈述；
- 失败清单可以与任务规则逐条对照，便于发现规则冲突、遗漏前提和边界条件；
- 即使最终不修改任何内容，一份整理过的失败清单也比一句「看起来没问题」更容易复核。

v0.1 的经验说明，独立错误线路本身没有显示出超过普通自检的收益，但这不等于失败枚举没有价值。v0.2 保留失败枚举，去掉没有证据支撑的概率层，把精力放在每条失败是否有可核对的依据上。

## 3. 为什么要求可验证证据

`review` 的每条 finding 必须尽量满足：

- `rule_quote` 必须取自任务原文或用户提供的 context（比较时归一化空白），避免模型把常识或臆测写成任务规则；
- 能给出可执行检查时使用 `check_kind=executable`，并记录检查内容与预期信号；
- 无法自动执行时标为 `manual`，证据不足或存在规则歧义时标为 `ambiguous`。

这样做的目的不是让模型更聪明，而是让输出更容易被否定：审阅者可以核对引文是否真的存在、检查是否真的能运行、预期信号是否明确。v0.2 仍然保留 `verify` 作为代码任务的主推模式，因为对 Python 函数而言，独立反例加隔离执行能提供比文字审查更硬的证据。即使如此，`checks_passed` 也只表示通过了列出的有限检查，不是正确性证明。

## 4. 闭环推理为什么不引入新信息

review 和 verify 都是模型对自己或对任务做多轮处理，其中可能存在「看起来更严谨」的错觉。需要明确：

- 模型重新阅读任务、整理自己的输出、按固定格式复查，能减少表述错误和遗漏，但不会凭空产生任务里没有的事实；
- 引用约束的是文本一致性，不保证引用的规则本身正确或完整；
- 可执行检查能引入真实的运行结果，这是闭环中少有的新信息，但检查由模型提出，覆盖范围受模型发现能力限制；
- 多轮自审与验证模式的差距在三轮实验里都没有稳定出现，说明不能假设「闭环轮次更多 = 结论更可靠」。

因此项目把这些流程定位为「整理证据、暴露失败」的工具，而不是推理增强或正确性保证。

## 5. 与三轮实验结论的对应

第一轮 30 道自建 Python 函数题：直接作答 26/30，五轮自审 28/30，原 DualPath 28/30，且后两者逐题结果完全一致；DualPath 的估算费用高约 22%。这说明当时增加的双线路、概率评估和多阶段汇聚，没有在已有样本上带来可观察的修复收益，概率层也没有被证明有用。继续把概率分级当作卖点缺乏依据。

第二轮 8 道自建题：直接作答 7/8，一轮自检 8/8，三轮自检在有结果的 6 题上 6/6（两题因接口/截断缺失），验证模式 7/8。验证模式没有修复或改坏任何一题，漏掉的 V008 被一轮自检修好；失效点主要是反例发现覆盖不足，而不是执行器误判。两轮都没有「DualPath 或验证模式优于普通自检」的证据。

第三批 8 道规则交互题：四个方法隐藏测试均 8/8（初稿全部正确，没有修复样本）；同样的调用预算下，默认发现检出 4/13 个预设变异体，规则交互发现检出 9/13（I005 上有一题回退），参考实现认可 24/24 个被接受案例的预期。这只说明反例覆盖存在方向性差异，不能据此宣称优越性，详见 [第三批结果报告](../reports/interaction-pilot-results.md)。

这些结果直接影响了 v0.2：

- 不新增概率或风险宣传；
- review 默认只产出少量 finding（默认 5 条），并限制模型调用次数（最多 4 次，失败发现格式重试时 5 次），避免用更多轮次冒充更可靠；
- 把研发重点放在引文约束、可执行检查和明确的失败状态上；
- 对 `--interaction-focus` 这类新选项保持实验性标注；第三批小样本只给出方向性证据（变异检出 4/13→9/13），不足以宣称能力。

## 6. 运行状态的取舍

review 不再用「成功/失败」二元表示结果，而是区分：

- `completed`：审阅完成，且有 supported finding，产出修正后的结果；
- `no_findings`：失败发现返回空清单，只发生草稿与发现两次调用，直接采用草稿；
- `draft_only`：完成审阅，但没有 supported finding，采用草稿；
- `probe_failed`：尝试获取失败清单时失败（模型错误、超时或结构校验未通过）；
- `review_failed`：审阅或修正阶段失败；
- `model_failed`：草稿阶段失败，没有可交付结果。

`no_findings` 不等于任务正确，`completed` 也不等于 finding 全部成立。状态的作用是让失败路径可见，而不是包装成成功。退出码保持简单：0 表示流程完成，2 表示未完成或输入/环境问题，130 表示用户取消。

## 7. v0.3 计划

- 移除 `dualpath run` 及概率分级相关代码、测试和文档入口；迁移方式在 v0.2 的 README 中提前说明。
- 保持 `review` 与 `verify` 的 JSON 结构稳定，避免在补丁版本中破坏已有记录的可解析性。
- 第三批已在新冻结题集上完成默认发现与 `--interaction-focus` 的比较（修复指标因初稿全对而未获得样本，变异检出 4/13 对 9/13）；后续应提高题目难度或先做初稿可错性筛选，再报告修复数、费用和退步。
- 不把 review 的 finding 数量或 verify 的通过题数当作正确性证明；如引入新证据源，需要单独说明其局限。

## 非目标

- 不做通用风险评分或概率预测；
- 不承诺 review 能发现所有失败，也不承诺 verify 覆盖所有输入；
- 不用更多模型调用轮次作为质量保证。
